# Study protocol — Version 0.1

## 1. Objective

Develop and evaluate an auditable biomedical retrieval-augmented generation system that retrieves evidence, generates an answer, records provenance, estimates evidence support, and abstains when the retrieved evidence is insufficient.

## 2. Why this is suitable for the available hardware

The study will use pre-trained retrieval representations and API-based generation rather than full retriever or generator training. CPU-heavy components will be limited by:

- compact document collections during pilot testing;
- batched embedding creation;
- cached embeddings;
- small top-k candidate sets;
- no local large-language-model inference;
- no full ANCE, FiD, or REALM training.

## 3. Primary research questions

**RQ1.** How much do biomedical dense retrieval and reranking improve evidence retrieval over BM25?

**RQ2.** Does evidence-linked generation improve answer accuracy and factual support compared with generation without retrieval and standard RAG?

**RQ3.** Can an evidence-sufficiency score support selective answering, reducing unsupported answers at an acceptable coverage level?

**RQ4.** What latency and local-resource trade-offs arise from lexical retrieval, dense retrieval, reranking, evidence verification, and generation?

## 4. Planned system variants

1. Generator only — no retrieval.
2. BM25 RAG.
3. Biomedical dense-retrieval RAG.
4. Dense retrieval plus reranking.
5. Proposed auditable RAG:
   - retrieval;
   - reranking;
   - evidence-linked answer generation;
   - evidence-support scoring;
   - abstention when support is below a threshold;
   - per-query audit log.

## 5. Evaluation categories

### Retrieval

- Recall@k
- Mean reciprocal rank
- Precision@k where supported by the dataset

### Answer quality

- Exact match for suitable question types
- Token-level F1
- List-answer F1 where applicable

### Evidence grounding

- Citation/evidence coverage
- Entailment or support score
- Unsupported-answer rate
- Evidence overlap with gold documents/snippets

### Selective answering

- Coverage
- Accuracy at retained coverage
- Risk–coverage curve
- Unsupported-answer reduction

### Efficiency

- Retrieval latency
- Reranking latency
- Generation latency
- End-to-end latency
- peak RAM where measurable
- index size and cache size

## 6. Dataset policy

The first dataset will be a public biomedical question-answering benchmark. The exact BioASQ release and task subset will be fixed only after access, licence, file structure, and task compatibility are verified.

A second public dataset will be added only if:

- it has a compatible answer/evidence structure;
- its licence permits the intended processing;
- it is feasible within 16 GB RAM and 50 GB disk;
- it adds genuine external validation rather than duplicating BioASQ.

No private EHR dataset will be used.

## 7. Reproducibility policy

Each run will save:

- input dataset identifier and checksum;
- code version;
- environment freeze;
- model names and revision identifiers where available;
- configuration;
- prompt template;
- raw Groq response;
- parsed answer;
- retrieved passages and scores;
- evaluation output;
- timestamps and latency;
- errors and retries.

## 8. Evidence gate

No manuscript result will be written until the corresponding CSV or JSON output exists and can be regenerated by a documented command.
